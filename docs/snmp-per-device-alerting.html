FlowScope · design · alerting

Per-device SNMP alerting.

Today every alert rule is a Go struct in internal/alerteng with one global parameter set. Operators want to say "this WAN interface alerts at 70%, those backbone uplinks at 90%", "page if the BGP peer to AS65001 on edge-1 goes down", or "alert when this vendor-specific power-supply OID returns notOK on any chassis I tag as core" — none of which the current shape expresses. This document lays out a templates-and-instances model with two flavors of template (built-in code and user-defined GUI-built), the schema and migrations to land it, and the order to ship the work in so each phase ships standalone value.

The model

Three concepts. Templates are the existing Go-coded rule types — they own the SQL, the violation copy, and the parameter shape. Instances are operator-created bindings of one template + one scope selector + one parameter set. Scope selectors are the small structured matcher language that binds an instance to a subset of devices, interfaces, or peers.

template (Go code) instance (settings row) scope selector engine implements / scopes

A template knows how to evaluate one kind of condition; it has no opinion about which devices it applies to. An instance picks a template, names it, sets parameters, and binds a scope. The engine no longer iterates rules — it iterates instances, and each violation is tagged with both the template ID (for grouping in the UI) and the instance ID (for ack/silence/dedup).

Two flavors of template

built-in code

Go structs in internal/alerteng/. Hand-tuned SQL, full read of any ClickHouse table, reviewed in PRs, shipped with the binary. This is where InterfaceUtilizationHigh, BGPNeighborDown, DeviceCPUHigh live. Adding one is a code change.

user-defined GUI

Constrained shape: data source × metric × comparison × threshold × dwell. No raw SQL. Stored as rows in alert_user_templates; evaluated by a single shared Go template that knows how to render any user-defined spec into a safe parameterized query. This is where "alert when this OID equals 2 for 60s" lives.

Both flavors register against the same template_id namespace and both are targets for instances. The UI presents them in one list with a small badge; operators don't need to care which kind backs a given rule, except that built-in templates can't be edited from the GUI (only their default-instance parameters can).

Schema

One new table, one column added to the existing event ledger, and the existing alert_rule_settings table stays in place as the seed source for one release. Migrations stay forward-only and idempotent per CLAUDE.md.

)

Scope selector — JSON shape

The selector is a structured matcher, not a DSL. Each field is a filter; an instance fires on the intersection of all non-empty filters. An empty selector matches everything (that's how default instances work).

{
  "exporters":        ["10.1.1.1", "10.1.1.2"],   // exact IPs (canonical exporter ID)
  "exporter_cidrs":   ["10.10.0.0/16"],            // CIDR matchers, OR'd with exporters
  "exporter_labels":  { "role": "wan_edge" },    // match against device_inventory labels
  "ifindex":          [1, 2, 3],                  // only meaningful for interface-scoped templates
  "ifname_glob":      "Gi0/0*",                  // glob on ifDescr / ifAlias
  "interface_labels": { "role": "uplink" },
  "bgp_peers":        ["192.0.2.1"],              // only meaningful for BGP-scoped templates
  "asn_remote":       [65001, 65002]              // ditto, by neighbor ASN
}

Template registry — Go side

// internal/alerteng/template.go

type ScopeSelector struct {
    Exporters       []netip.Addr
    ExporterCIDRs   []netip.Prefix
    ExporterLabels  map[string]string
    IfIndex         []uint32
    IfNameGlob      string
    InterfaceLabels map[string]string
    BGPPeers        []netip.Addr
    ASNRemote       []uint32
}

type Template interface {
    ID() string                                    // stable, e.g. "interface_utilization_high"
    DefaultParams() map[string]any
    DefaultSeverity() string
    Runbook() string
    Evaluate(ctx context.Context, conn driver.Conn,
             scope ScopeSelector, params map[string]any) ([]Violation, error)
}

Engine changes

The current engine loop in internal/alerteng/engine.go iterates a []Rule and calls r.Evaluate(ctx, conn). Two surgical changes:

  1. Loader switches to instances. LoadRules becomes LoadInstances: it returns []InstanceRule where each InstanceRule closes over (template, scope, params, instance_id, severity). Refresh-tick semantics (max(updated_at) version stamp) carry over unchanged.
  2. Templates accept scope. Each existing rule struct gets a refactor: pull the SQL into a method that takes a scopeWhere string, accept params as a typed struct via the loader, return violations. The same helper that generates scopeWhere from ScopeSelector is shared across templates so the matching semantics stay consistent.

The alert-key shape changes from (rule_id, scope, group_key) to (instance_id, scope, group_key). This is the breaking part: in-flight open alerts created under the old keying need a one-time bridge so a deploy doesn't dupe-fire every open alert. The bootstrap logic at engine.go:260 handles this — see Migration path below.

Why instance-keyed and not (template + scope)-keyed? Two instances of the same template with overlapping scopes are legitimate (e.g. "all WAN at 80% warn" + "transit-only at 70% page"). Keying on instance_id keeps them as separate alerts the operator can ack independently. Cross-instance dedup is a UI grouping concern, not an engine concern.

User-defined templates

Operators build these in the GUI. The constraint model is small on purpose — you pick from a list of vetted data sources and a list of comparison ops, never write SQL. The shared evaluator translates the spec into a parameterized ClickHouse query at runtime; if the operator's spec doesn't compile (unknown source, bad comparison), the API rejects the row at write time, not at evaluate time.

The five-field spec

fieldoptionsexample
sourcedevice_resource_samples · iface_counter_samples · bgp_peers · device_inventory · device_oid_samplesdevice_oid_samples

Scope is not part of the template — it lives on the instance, same as for built-in templates. So one user-defined template ("PSU not OK") can have three instances scoped to different device groups with different severities and channels.

New · snmp_custom_oids + device_oid_samples

To alert on an OID, the SNMP service needs to be polling it. The first table is the operator's "tell SNMP what to walk" instruction; the second is where samples land for templates to read.

-- 000021_custom_oids.sql
CREATE TABLE IF NOT EXISTS snmp_custom_oids
(
    oid_id          String,                              -- UUID
    oid             String,                              -- e.g. '1.3.6.1.4.1.9.9.117.1.1.2.1.2'
    name            String,                              -- 'Cisco PSU oper status'
    scope_json      String  DEFAULT '{}',                   -- which exporters to walk — same ScopeSelector shape as instances
    walk_seconds    UInt32  DEFAULT 60,                    -- per-OID cadence; scheduler enforces a floor
    is_table        UInt8   DEFAULT 0,                     -- 0=GET, 1=GETNEXT walk; affects how many samples land per cycle
    value_kind      LowCardinality(String) DEFAULT 'numeric', -- 'numeric' | 'string' | 'octets'
    enabled         UInt8   DEFAULT 1,
    created_at      DateTime64(3, 'UTC'),
    updated_at      DateTime64(3, 'UTC'),
    updated_by      String  DEFAULT 'anonymous'
)
ENGINE = ReplacingMergeTree(updated_at)
ORDER BY oid_id;

CREATE TABLE IF NOT EXISTS device_oid_samples
(
    polled_at       DateTime64(3, 'UTC'),
    exporter        IPv6,                                -- canonical exporter ID, v4-mapped for IPv4
    oid_id          String,                              -- FK to snmp_custom_oids.oid_id (no enforced constraint, just convention)
    oid             String,                              -- denormalized for query convenience
    instance_index  String  DEFAULT '',                    -- for table OIDs, the trailing index (e.g. '.1', '.2')
    value_numeric   Float64 DEFAULT 0,
    value_string    String  DEFAULT '',
    walk_status     LowCardinality(String)               -- 'ok' | 'timeout' | 'noSuchObject' | 'authFail'
)
ENGINE = MergeTree
PARTITION BY toYYYYMMDD(polled_at)
ORDER BY (exporter, oid_id, polled_at)
TTL polled_at + INTERVAL 30 DAY;

The shared evaluator

// internal/alerteng/user_template.go
//
// UserDefinedThreshold is the single Go template that backs every
// row in alert_user_templates. The engine instantiates one of these
// per user-defined template at load time, closes over the spec, and
// reuses the same Evaluate path as built-in templates.

type UserDefinedThreshold struct {
    spec UserTemplateSpec  // loaded from alert_user_templates row
}

func (t UserDefinedThreshold) Evaluate(
    ctx context.Context, conn driver.Conn,
    scope ScopeSelector, params map[string]any,
) ([]Violation, error) {
    sql, args := buildUserQuery(t.spec, scope)   // pure function, fully tested
    rows, err := conn.Query(ctx, sql, args...)
    // … standard violation construction, dwell-window check, etc.
}
Why a single Go template instead of generating one struct per user template? Keeps the safe surface tiny: one place where source × metric × comparison turn into SQL, one place to test for injection, one place to add a new data source. Operator-defined rows in alert_user_templates are pure data — no codegen, no plugin loader, no Wasm sandbox.

Migration path

Five phases. Each ships standalone — phase 1 alone gets you per-device thresholds for everything except BGP, and phase 2 lights up BGP. Phases 3–5 sand off the rough edges.

PHASE 0

Today · what already works

no code changes
  • Rules live in internal/alerteng/rules*.go, DefaultRules() is the static set.
  • Operators tweak parameters globally via alert_rule_settings (migrations/000005_settings.sql:124).
  • Per-(exporter,component) granularity already exists for the device-health rules — just no per-(exporter,component) thresholds.
PHASE 1

Land the instance model · ship the per-device thresholds for existing rules

migration 000017 · alerteng refactor · settings UI v2
  • Migration 000017_alert_rule_instances.sql: CREATE TABLE alert_rule_instances + ALTER alert_events ADD COLUMN instance_id.
  • Refactor existing rule structs to implement the new Template interface; introduce scopeWhere helper; rewrite engine loop to iterate instances.
  • Seed step (one-shot, in migration 000017): for every alert_rule_settings row, INSERT INTO alert_rule_instances a row with template_id = old.rule_id, scope_json = '{}', params_json = old.params_json, is_seed = 1. For built-in rules with no override row, the API inserts a default-instance row on first read (so the engine has something to evaluate).
  • Open-alert bridge: the engine bootstrap at engine.go:260 reads the existing 7-day open set; on first-tick after migration, any open row with instance_id = '' is reattributed to the seed instance for its rule_id before being placed in the in-memory open map. No close/re-open events emitted.
  • Settings UI gets a "Rules" page listing instances grouped by template, with a "Create from template" wizard. The seed instances surface as "Default · all devices" rows with an info chip explaining where they came from.
  • alert_rule_settings stays in place but becomes read-only; the API logs a warning if anything tries to write to it. Drop it in phase 5.
PHASE 2

BGP ingest + BGPNeighborDown template

migration 000018 · snmp service · new template
  • Migration 000018_bgp_peers.sql: CREATE TABLE bgp_peers (exporter, peer_addr, peer_asn, local_asn, state, established_at, last_change_at, polled_at, …). Same argMax(state, polled_at) shape the device-health tables already use.
  • SNMP scheduler walks bgpPeerTable (1.3.6.1.2.1.15.3.1) and the Cisco/Juniper analogues (cbgpPeer2Table, jnxBgpM2PeerTable) on the same per-device cadence as existing walks. Source goes in a source column the same way device_resource_samples does.
  • New template BGPNeighborDown in internal/alerteng/rules_bgp.go: fires when argMax(state, polled_at) != 'established' for at least established_min_s seconds. Scope selector understands bgp_peers and asn_remote.
  • UI: new template appears in the "Create from template" wizard automatically. No schema changes to alert_rule_instances — the selector fields for BGP were already in the JSON shape from phase 1.
PHASE 3

Label-based scoping (role=wan_edge etc.)

device labels · interface labels · selector evaluator
  • Add labels Map(String,String) columns to device_inventory and to whatever interface-metadata table the SNMP service already maintains.
  • Operator-editable label assignment in the Devices view (Settings → Devices → Edit labels).
  • scopeWhere helper learns to translate exporter_labels / interface_labels into joins against those label columns.
  • This is the phase that unlocks "all WAN edges at 70%" without enumerating IPs. Without it, scope is exact-match-only — usable but not great.
PHASE 4

Preview-as-you-type · scope hygiene

UI polish · trust building
  • POST /api/alerts/instances/{id}/preview wired into the wizard: as the operator builds a selector, the right pane shows the matching set of devices/interfaces/peers in real time.
  • Conflict detector: warn when a new instance's scope overlaps an existing instance's scope on the same template (so two rules don't quietly fire on the same target).
  • "What would this rule have alerted on in the last 24h?" backfill query — runs the new instance's SQL across the warm tier and shows the would-be event count before the operator saves.
PHASE 5

User-defined templates against existing data

migration 000020 · alerteng evaluator · template builder UI
  • Migration 000020_user_templates.sql: CREATE TABLE alert_user_templates.
  • Add UserDefinedThreshold Go template + the buildUserQuery pure function. Source whitelist starts with the four tables we already populate: device_resource_samples, iface_counter_samples, bgp_peers, device_inventory. flows is deliberately excluded — too high-cardinality for safe ad-hoc thresholds.
  • Loader extends to read both alert_user_templates and the built-in registry, register each row as a UserDefinedThreshold, and present them in GET /api/alerts/templates alongside built-ins (with a kind: "user" field).
  • Settings UI gets a "Templates" tab with a "+ New custom template" form — source picker, metric picker, comparison + threshold + dwell, default severity. After save, the existing instance wizard can target the new template.
  • This phase delivers the headline ask without any new ingest work: operators can already alert on anything we're polling. OID-level customization comes in phase 6.
PHASE 6

Custom OID polling · arbitrary-OID alerts

migration 000021 · snmp scheduler · OID admin UI
  • Migration 000021_custom_oids.sql: CREATE TABLE snmp_custom_oids + device_oid_samples.
  • SNMP scheduler grows a "custom OID" lane that reads snmp_custom_oids on its refresh tick, schedules walks per (oid_id, exporter) at the configured cadence (with a hard floor — say 30s — to prevent self-DoS), and writes results to device_oid_samples. The credential resolution path is unchanged: the existing per-device v2c/v3 binding is reused.
  • device_oid_samples is added to the user-defined template source whitelist. Filter shape for this source includes oid_id (or oid) and instance_index so a single template can target a row in a table OID.
  • Settings UI gets an "SNMP → Custom OIDs" page: paste an OID, name it, pick scope, pick cadence, hit "Test" to walk it once and see the value before committing. Once it's polling, "+ New template from this OID" deep-links into the template builder with the OID pre-filled.
  • (Nice-to-have, not a blocker for shipping the phase) MIB browser: bundle a curated set of vendor MIBs and let the operator pick by name instead of pasting an OID. Pure UX sugar — the schema and engine don't care.
PHASE 7

Drop the legacy table

migration 000022 · cleanup
  • Migration 000022_drop_alert_rule_settings.sql: DROP TABLE IF EXISTS alert_rule_settings. Safe because phase 1's seed already copied everything; the table has been read-only for several release cycles.
  • Remove the deprecated read path from internal/alerteng/loader.go.
  • Remove the is_seed distinction from the UI (or keep it as a low-priority badge — operators sometimes want to know "this is the default someone never customized").

Backwards compatibility & risk

Open alerts

The bootstrap bridge in phase 1 reattributes pre-migration open rows to seed instances before the first evaluation tick. Net effect: no spurious close + re-open on deploy.

Webhook payloads

Add instance_id + instance_name as new fields. Existing fields (rule_id, severity, scope, group_key) stay populated. No breaking change for downstream consumers.

OpenAPI / TS client

Per CLAUDE.md, edit api/openapi.yaml first, run make gen-client, then implement the Go handlers. The contract test in CI catches drift.

Engine throughput

One SELECT per instance per tick instead of one per template. With ~50 instances on a typical deployment, that's still well under the 10s tick — but the loader needs a per-template result-set cache so two instances with different parameters but identical SQL don't run the query twice.

Selector validation

Validate scope at write time, not evaluate time. Rejecting a malformed CIDR at POST /api/alerts/instances is recoverable; the alert engine quietly skipping evaluations because of a bad selector is not (silent failures are explicitly forbidden).

Test coverage

The integration tests at internal/alerteng/evaluator_*_integration_test.go already cover the device-health rules; adapt them to instantiate templates with explicit scope/params instead of constructing rule structs directly. Add new fixtures for scope filtering (one device matches, one doesn't, instance fires only on the matching one).

The "ultimate customization" comes from the selector plus the user-defined template builder — built-in templates cover the common asks safely, user-defined templates fill in the long tail, and the same instance + scope model applies on top of both. The "simplicity" comes from the fact that templates and parameters look exactly like they do today for anyone who doesn't open the new UI: they keep getting the same default-instance behavior they have now.
